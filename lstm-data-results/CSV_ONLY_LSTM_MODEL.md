# CSV-only LSTM forecasting model

## Purpose

The CSV-only LSTM is a short-term, multi-output forecasting model for the
simulated European low-voltage feeder. It reads only time-aligned CSV files. It
does **not** query Neo4j, use feeder graph connectivity, or depend on PyTorch
Geometric.

For every forecast origin, the model answers this question:

> Given the previous 30 one-minute observations of feeder loads, bus voltages,
> and line currents, what will every bus voltage and every line current be for
> each of the next 15 minutes?

This is therefore not a load-only model. Deployment would require recent
voltage and current measurements as well as recent load measurements.

The implementation is divided among:

- [`scripts/lstm_dataset.py`](../scripts/lstm_dataset.py): CSV loading,
  validation, optional standardization, and forecast-window construction.
- [`scripts/lstm_model.py`](../scripts/lstm_model.py): neural-network
  architecture and forward prediction.
- [`scripts/train_lstm.py`](../scripts/train_lstm.py): configuration, training,
  checkpoint selection, testing, metrics, and result export.

## End-to-end pipeline

```text
European LV feeder CSV definitions and one-minute load profiles
                              |
                              v
                  OpenDSS daily power-flow simulation
                              |
                              v
       load_profiles.csv + bus_voltages.csv + line_currents.csv
                              |
                              v
       row alignment, finite-value checks, voltage phase collapse
                              |
                              v
         optional training-fitted per-feature standardization
                              |
                              v
                  chronological 70/15/15 split
                              |
                              v
        30-minute histories -> 15-minute future target windows
                              |
                              v
     PCA compression + level/difference encoders + one-layer LSTM
                              |
                              v
       horizon-conditioned voltage/current residual correction
                              |
                              v
        correction + training-fitted trend baseline = forecast
                              |
                              v
        validation checkpointing -> held-out test evaluation
```

## Data generation and files

The three input files are generated by
[`scripts/generate_labels.py`](../scripts/generate_labels.py). That script
builds the European LV circuit from the CSV definitions in
`data/European_LV_CSV`, applies the per-minute load profiles, and solves an
OpenDSS daily power flow at one-minute resolution for 1,440 timesteps.

The LSTM consumes the generated files in `data/Computed`:

| File | Rows | Raw feature columns | Meaning |
|---|---:|---:|---|
| `load_profiles.csv` | 1,440 | 55 | Active power for loads `LOAD1` through `LOAD55`, in kW |
| `bus_voltages.csv` | 1,440 | 2,721 | Per-phase bus voltage magnitudes, in per unit (Vpu) |
| `line_currents.csv` | 1,440 | 905 | Maximum current magnitude reported for each line, in amperes |

Each row represents the same one-minute timestep in all three files. Loading
stops with an error if their indices are not identical. All numeric values are
converted to `float32` tensors, and training stops if any CSV contains a NaN or
infinite value.

### Voltage target preparation

OpenDSS exports voltage columns with phase suffixes such as `1.1`, `1.2`, and
`1.3`. The loader groups columns by the text before the first period and takes
the minimum available phase voltage at each bus:

```text
bus voltage at time t = min(phase-1 Vpu, phase-2 Vpu, phase-3 Vpu)
```

Using the minimum phase gives a conservative bus-level voltage target. It also
reduces the raw 2,721 phase columns to 906 bus targets. `SourceBus` is excluded,
matching the project's graph-model convention.

This collapse deliberately discards phase-specific voltage information. The
model forecasts the minimum bus voltage, not voltage unbalance or every phase
separately.

### Current target preparation

There is one target column for each of the 905 lines. During data generation,
OpenDSS current magnitudes are read for the active line and the maximum
magnitude is stored. The resulting target represents a conservative line-level
current magnitude rather than a separate forecast for every conductor.

## Chronological split and forecast windows

The split is chronological; rows are never randomly divided:

| Partition | Fraction | Timestep range | Forecast windows |
|---|---:|---:|---:|
| Training | 70% | `[0, 1007)` | 963 |
| Validation | 15% | `[1007, 1223)` | 202 |
| Test | remaining 15% | `[1223, 1440)` | 203 |

The exact row counts follow Python's `int()` truncation. Validation controls
the learning-rate scheduler, early stopping, and checkpoint selection. Test
targets are used only after the best checkpoint has been restored.

Each dataset item uses an origin timestep `t` and contains:

| Tensor | Shape before batching | Contents |
|---|---|---|
| `load_history` | `[30, 55]` | Loads from `t-29` through `t` |
| `voltage_history` | `[30, 906]` | Bus voltages from `t-29` through `t` |
| `current_history` | `[30, 905]` | Line currents from `t-29` through `t` |
| `voltage_targets` | `[15, 906]` | Voltages from `t+1` through `t+15` |
| `current_targets` | `[15, 905]` | Currents from `t+1` through `t+15` |

A target horizon must remain completely inside its partition. Input history is
allowed to extend before a validation or test boundary because those values
would already be known at forecast time. This does not expose future targets.

Training windows overlap heavily. Adjacent samples share 29 of 30 history
rows and 14 of 15 target rows. The nominal window count is therefore much
larger than the number of independent operating scenarios.

## Optional normalization and scaling

`NORMALIZE_DATA` in `scripts/train_lstm.py` selects the data space used by the
model and training loss.

### `NORMALIZE_DATA = True`

For every load, bus, and line feature independently, the code fits a mean and
population standard deviation using training timesteps only:

```text
z = (x - training_mean) / training_standard_deviation
```

Standard deviations are clamped to at least `1e-6` to prevent division by
zero. The fitted statistics are then reused for validation and test data. This
keeps information from later partitions out of preprocessing.

Per-feature standardization is normally important here because voltage is
close to 1 Vpu with very small variance, while currents and loads have much
larger numerical scales. It also prevents high-current lines from dominating
other lines solely because of their units and magnitude.

### `NORMALIZE_DATA = False`

The code creates identity transforms with mean zero and standard deviation one.
All model inputs, targets, PCA fitting, trend fitting, and losses then operate
directly in the original CSV units. The same prediction code still works
because the final inverse transform is also an identity operation.

Raw-unit mode is intended as an experiment. A voltage loss measured in Vpu
squared can be orders of magnitude smaller than a current loss measured in
amperes squared. The voltage and current lambda values may therefore need very
different settings in raw mode. Changing `NORMALIZE_DATA` also changes the
meaning of the Huber `delta` parameter.

The chosen mode is saved as `normalize_data` and `model_data_space` in
`lstm-data-results/config.json`. The scaler or identity-transform tensors are
saved in the model checkpoint.

## Training-only PCA spatial bases

Directly decoding 906 voltages and 905 currents from every horizon would
create a large output layer and allow unrelated corrections at neighboring
feeder elements. The model instead uses low-rank spatial bases fitted only on
the training interval:

- Voltage: 906 features -> 16 PCA components.
- Current: 905 features -> 64 PCA components.

`torch.pca_lowrank` fits each basis with `center=False` and four iterations.
When standardization is enabled, training values have already been centered
per feature. The bases are fixed buffers, not trainable parameters.

History is projected into these spaces:

```text
voltage_latent = voltage_history @ voltage_basis       # 906 -> 16
current_latent = current_history @ current_basis       # 905 -> 64
```

The output heads also predict in latent space. Their corrections are mapped
back to feeder-wide outputs with the transposed bases. This restricts learned
corrections to spatial patterns found in training data and reduces the number
of trainable output parameters.

PCA is dimensionality reduction, not the optional per-feature scaling flag.
It is still used when `NORMALIZE_DATA` is `False`.

## Training-fitted trend baseline

The neural network does not forecast the complete electrical state from
scratch. It learns a correction around a strong trend baseline.

For each history window and feature, the recent 30-minute slope is:

```text
slope = (value_at_t - value_at_t_minus_29) / 29
```

For each target feature and each horizon from 1 to 15, training data is used to
fit a coefficient that relates this recent slope to the actual future change:

```text
coefficient[h, feature]
    = sum(slope * future_change[h]) / sum(slope^2)
```

Coefficients are made finite and clipped to `[-20, 20]`. The baseline is then:

```text
baseline[h] = latest_observation + slope * coefficient[h]
```

Voltage and current have separate feature- and horizon-specific coefficients.
All coefficients are fitted only from valid training windows and stored as
non-trainable model buffers.

Because the learned output heads start with zero weights and biases, the
initial epoch-0 model outputs exactly this trend baseline. Training only has to
learn useful residual corrections.

## Neural-network architecture

Let `B` be the batch size, `W=30` the history length, `H=15` the forecast
horizon, and `D=128` the current hidden size.

### 1. Levels and one-step differences

For each modality, the model concatenates its level with its one-step change:

```text
difference[:, 0] = 0
difference[:, t] = level[:, t] - level[:, t-1]
encoder_input = concatenate(level, difference)
```

This makes both the current operating point and short-term movement explicit.

### 2. Separate modality encoders

The three inputs are encoded separately so the small load vector is not
overwhelmed by the much wider voltage and current vectors:

| Modality | Encoder input width | Encoder output width |
|---|---:|---:|
| Loads | `2 * 55 = 110` | 64 |
| PCA voltage | `2 * 16 = 32` | 96 |
| PCA current | `2 * 64 = 128` | 96 |

Each encoder is a linear layer followed by GELU.

### 3. Fusion

The three 30-step encoded sequences are concatenated to width 256. A fusion
block maps each timestep from 256 to 128 features using:

```text
Linear -> GELU -> LayerNorm
```

### 4. LSTM sequence encoder

The fused sequence `[B, 30, 128]` enters a batch-first LSTM. The current
configuration uses one layer and a 128-dimensional hidden state. Only the last
output state is retained and normalized:

```text
last_hidden = LayerNorm(lstm_sequence[:, -1, :])
```

`DROPOUT=0.2` is supplied to the model. PyTorch's internal LSTM dropout only
acts between stacked LSTM layers, so it is inactive with one LSTM layer. The
decoder described below still applies 0.2 dropout.

### 5. Horizon-conditioned decoder

A single LSTM summary must produce 15 different future steps. The model learns
one 128-dimensional embedding for each horizon minute. It adds each embedding
to the final LSTM state and processes all horizons in parallel:

```text
future_hidden[h]
    = forecast_block(last_hidden + horizon_embedding[h])
```

The forecast block is `Linear -> GELU -> Dropout`. Horizon conditioning tells
the shared decoder whether it is producing minute 1, minute 2, ..., or minute
15. Without it, the shared learned correction would tend to be identical at
all horizons.

This is direct multi-horizon forecasting: all 15 steps are produced in one
forward pass. It avoids autoregressive error accumulation because minute 15
does not consume the model's prediction for minute 14. The tradeoff is that
the decoder does not explicitly enforce smoothness between adjacent future
minutes.

### 6. Separate voltage and current residual heads

The shared decoded states feed two linear heads:

```text
voltage head: 128 -> 16 latent corrections -> 906 bus corrections
current head: 128 -> 64 latent corrections -> 905 line corrections
```

The final predictions are:

```text
voltage_prediction = voltage_trend_baseline + voltage_correction
current_prediction = current_trend_baseline + current_correction
```

With the current data dimensions and configuration, the model has approximately
216,912 trainable parameters. PCA bases and trend coefficients are buffers and
are not counted as trainable parameters.

## Loss function and head weighting

The loss is computed separately for voltage and current, then combined:

```text
total_loss = lambda_voltage * voltage_loss
           + lambda_current * current_loss
```

The current code defaults are:

```text
LOSS_FUNCTION = "huber"
HUBER_DELTA = 1.0
LAMBDA_VOLTAGE = 0.7
LAMBDA_CURRENT = 1.0
```

These lambda values give the current head more influence than the voltage
head. Each head loss uses a mean reduction, so the similar counts of buses and
lines do not multiply either loss merely because there are many outputs.

For an error `e`, Huber loss is:

```text
0.5 * e^2                         when abs(e) < delta
delta * (abs(e) - 0.5 * delta)    otherwise
```

It behaves quadratically for ordinary errors and linearly for large errors,
making it less dominated by rare current spikes than MSE. With standardized
data, `delta=1.0` is approximately a one-training-standard-deviation transition
for each feature. With raw data, the same delta means 1 Vpu for voltage and 1 A
for current, so separate tuning should be considered.

Setting `LOSS_FUNCTION = "mse"` switches both heads to mean squared error. The
test metrics are always calculated in physical units regardless of which
training loss is selected.

## Optimization and regularization

The current script defaults are:

| Setting | Value |
|---|---:|
| Batch size | 32 |
| Maximum epochs | 100 |
| Initial learning rate | `5e-5` |
| Optimizer | AdamW |
| Weight decay | `1e-4` |
| Gradient-norm limit | `1.0` |
| Early-stopping patience | 20 epochs |
| Scheduler patience | 5 epochs |
| Scheduler reduction factor | `0.5` |
| Minimum learning rate | `1e-5` |
| Random seed | 42 |

Training batches are shuffled. Validation and test batches preserve order.
CUDA is selected automatically when available; otherwise training uses the
CPU. Pinned DataLoader memory is enabled only for CUDA.

For every training batch, the script:

1. Moves histories and targets to the selected device.
2. Clears AdamW gradients.
3. Runs the model for voltage and current predictions.
4. Calculates and combines the two losses.
5. Backpropagates the total loss.
6. Clips the global gradient norm to 1.0.
7. Applies an optimizer step.

At the end of each epoch, validation loss is calculated without gradients.
`ReduceLROnPlateau` monitors the weighted validation total and halves the
learning rate after five non-improving epochs, down to `1e-5`.

## Checkpoint selection and early stopping

Before optimization, epoch 0 is evaluated and saved. Because both residual
heads are zero-initialized, this checkpoint represents the training-fitted
trend baseline. This gives training a safe reference point.

A trained epoch replaces the checkpoint only when:

1. Its weighted total validation loss is lower than the current best total.
2. Its voltage validation loss is no worse than the epoch-0 voltage loss.
3. Its current validation loss is no worse than the epoch-0 current loss.

The second and third conditions are a Pareto safeguard: the model cannot select
a checkpoint that improves one output head by sacrificing the other relative
to the trend baseline.

The stale-epoch counter resets after a valid checkpoint improvement. Training
stops after 20 consecutive epochs without one. The best checkpoint is then
restored before test prediction.

## Baselines

Every test run evaluates the LSTM beside two non-neural baselines.

### Persistence

Persistence repeats the most recent observed voltage and current at all 15
future horizons:

```text
prediction[t+h] = observation[t]
```

This is a necessary short-term forecasting reference because electrical states
usually change gradually.

### Training-fitted trend

The trend baseline uses the recent 30-minute slope and the training-fitted
horizon coefficients described earlier. Since this is also the LSTM's residual
anchor, comparing against it shows whether the neural correction adds value.

## Test metrics

Predictions and targets are converted back to physical units before metrics
are calculated. In raw mode, this conversion is an identity operation.

The following metrics are reported independently for voltage in Vpu and current
in amperes:

- **MAE:** mean absolute error.
- **MSE:** mean squared error, in Vpu squared or A squared.
- **RMSE:** square root of MSE, in Vpu or A.
- **R2:** `1 - sum_squared_error / total_target_sum_of_squares`.
- **Maximum absolute error:** largest individual absolute error.

Overall metrics flatten all test windows, all 15 horizons, and all buses or
lines into one collection. R2 is therefore a single global value; it is not an
average of per-batch R2 scores. Because forecast windows overlap, the same
physical timestep can appear at several horizons and is weighted once for each
appearance.

The script also calculates the same metrics separately for forecast minutes 1
through 15. Finally, it reports the LSTM's percentage RMSE improvement over
persistence for voltage and current.

## Running and configuring the model

From the project root, activate the project environment and run:

```powershell
conda activate KG_Energetics
python scripts/train_lstm.py
```

The main settings are constants near the top of `scripts/train_lstm.py`. For
example, to compare raw data against standardized data:

```python
NORMALIZE_DATA = True   # training-only per-feature standardization
NORMALIZE_DATA = False  # original CSV units
```

Change one experimental variable at a time and preserve each run's result
directory before starting the next run, because the default output filenames
are reused.

## Interpretation and limitations

- **Only one simulated day is available.** The 963 overlapping training
  windows do not represent 963 independent days or operating scenarios. A
  larger network can easily memorize the early part of the day and fail on the
  later validation interval.
- **There is chronological distribution shift.** Training, validation, and
  test correspond to different parts of a single day. Changes in the operating
  regime can dominate small architecture or loss improvements.
- **Future loads are unknown.** The model sees load history but no forecast of
  loads during the next 15 minutes. Abrupt future load and current changes that
  are not visible in history cannot be predicted reliably.
- **The feeder structure is implicit.** Fixed CSV column order and PCA capture
  correlations, but the model has no explicit buses, lines, connectivity, or
  electrical parameters. It cannot naturally transfer to a feeder with a
  different topology or feature ordering.
- **PCA restricts corrections.** Low-rank output improves regularization and
  coherence but may suppress localized events outside the retained training
  subspace.
- **Voltage phases are collapsed.** Minimum Vpu is useful for conservative
  voltage monitoring but cannot describe phase imbalance.
- **Line current is collapsed.** Maximum current magnitude does not preserve
  conductor-specific behavior.
- **Direct decoding has no explicit future continuity constraint.** Horizon
  embeddings allow different future steps, but adjacent predictions are not
  recursively connected.
- **Raw-unit training is deliberately unbalanced unless lambdas compensate.**
  Disabling standardization changes loss scales, PCA behavior, Huber delta
  interpretation, gradient balance, and potentially the best learning rate.
- **A strong baseline remains essential.** If the learned checkpoint cannot
  beat persistence and the fitted trend on genuinely unseen days, the extra
  LSTM complexity is not yet justified.

The most important path to a more reliable model is adding multiple simulated
or measured days with diverse load patterns, preserving an untouched final day
for evaluation, and supplying future load forecasts when they would be
available operationally.
